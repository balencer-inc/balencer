# AI審査員4人（下書きの採点）

書いた本人が自己採点すると甘くなる。だから**採点は書き手とは別のサブエージェント**にやらせる。
松浦勝人式の⑤にあたる工程（出典・全体像は [docs/_knowledge/marketing-matsuura-method.md](../../../docs/_knowledge/marketing-matsuura-method.md)）。

`brand-lint` とは役割が違う。機械で判定できる違反は `brand-lint`、**文章として弱いかどうか**はこの審査員。両方通す。

```
下書きを書く → ai-judges（4人で採点・弱点抽出）→ 直す → brand-lint（機械検品）→ 阿部さんに報告
```

## 実行手順

1. 採点対象の下書きをファイルに保存する（未保存なら先に保存。審査員はファイルパスで読む）
2. **Agentツールで4人を同時に起動する**（1メッセージ内で4つのtool useを並べる＝並列実行）。審査員ごとのプロンプトは `assets/judges.md` からそのまま使う
3. 4枚の採点票を受け取り、下の判定ルールで出す/直すを決める
4. 直す場合は自分（書き手）が直す。**審査員に書き直させない**（採点者と書き手を分ける意味がなくなる）
5. 直したら再採点は**1回だけ**。2周して80点に届かないならネタか切り口の問題なので、阿部さんに「この切り口では弱い」と正直に報告する

### 4人に渡す素材の違い（重要）

| 審査員 | 渡すもの |
|---|---|
| ①一流編集者 | 下書き本文のみ |
| ②SNS担当 | 下書き本文＋媒体（X/FB/note等）＋`.claude/skills/marketing/SKILL.md` の媒体別フォーマット規定 |
| ③阿部さんを知らない経営者 | **下書き本文だけ。`abe-takayuki.md` も会社資料も渡さない** |
| ④編集長 | 下書き本文＋`docs/company/BALENCER_MASTER_CONTEXT.md`＋`.claude/skills/marketing/assets/abe-takayuki.md` |

③に背景を渡すと「読めば分かる」で通してしまい、読者代表の意味が消える。ここは徹底する。

## 採点の設計

各審査員100点満点（4観点×25点）。観点は `assets/judges.md` に定義。

**採点の前に、まず一言の違和感を書かせる。** 「なんか変じゃないですか」「言い過ぎかな」という雑な違和感の方が、禁止ルールの列挙より効く（松浦式④）。観点表から入ると減点法の作文になるので、順番は必ず 違和感 → 点数 → 直す提案。

## 判定ルール

| 状態 | 対応 |
|---|---|
| 4人平均80点以上 かつ 最低点70点以上 | 出してよい。brand-lint へ進む |
| 平均80点未満 | 直して再採点（1回まで） |
| どれか1人が70点未満 | 平均が足りていても、その審査員の指摘箇所は直す |
| 編集長が「出さない」判定 | 点数に関係なく止める。理由を阿部さんに報告 |

点数は絶対値でなく**弱い箇所を特定するための道具**。「82点でした」だけの報告はしない。**誰が何を弱いと言い、どう直したか**を報告する。

## 事実検証は人間（ここはAIに任せない）

数字・役職・固有名詞・エピソードは審査員も間違いを見抜けない。審査員が「事実の裏取りが必要」と挙げた箇所は【要確認】を付けて阿部さんに出す。
松浦さんは英語版でAIが架空のキャンペーンを創作し3言語版を全削除する事故を起こしている。**盛られた事実は審査を通り抜ける**という前提で扱う。

## 使う場面

- SNS下書き（X長文・FB語り直し・note）を出す前
- 提案書・営業メール・LPのコピーを阿部さんに見せる前
- 過去に阿部さんの手直しが多かった種類の文書

短いもの（Xの140字単発・定型連絡文）には使わない。4人起動のコストが見合わない。
