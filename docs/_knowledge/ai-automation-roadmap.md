## 6. 請求書スキルの設計シード（2026-09-03 起票）

> OSAKA共創LAB（ファイアープレイス宛）の請求書を1枚作る過程で、**毎回詰まる場所は請求書の書式ではなく「会社の定数がどこにも記録されていないこと」**だと分かった。次のセッションはここから始める。

### 起票の経緯

ファイアープレイス様への請求書（2026年8月分＋7月イベント分）を作成。契約書から報酬条件を読み取る作業自体は10分で終わったが、**リポジトリ内を検索しても以下が1件も見つからなかった**:

- 適格請求書発行事業者登録番号（T＋13桁）
- 振込先口座
- 請求書番号の連番ルール
- 過去の請求書テンプレート（`docs/estimates/` に見積はあるが請求書はゼロ）

つまり自動化の第一歩はスクリプトではなく**定数の正本化**。ここを作れば2回目以降の発行が一気に速くなる。

### 作るもの2つ

**① `docs/company/invoice-constants.md`（先に作る・これが本体）**

| 記録する項目 | 備考 |
|---|---|
| 適格請求書発行事業者登録番号 | T＋13桁 |
| 会社名・住所・代表者名 | 契約書と同一表記で |
| 振込先口座 | 金融機関・支店・種別・番号・名義（カナ） |
| 請求書番号の付与ルール | 例 `INV-2026-001` の連番。採番済みの最新を1行で持つ |
| 締め・支払サイトの既定 | バレンサー標準＝末日締め翌月末払い |
| 発行済み請求書の台帳 | 1請求1行（宛先・件名・金額・発行日・入金確認） |

※ 口座番号を git に置くかは判断が必要。**`99_local/` 相当に置いてポインタだけ git、が安全側。**次セッションで阿部さんに確認する。

**② `.claude/skills/invoice`（`estimate` スキルの構成をそのまま踏襲する）**

`estimate` は「HTML＋CSV＋PDFの3点セット、検算込み」で成立している。請求書も同じ形にする。

固定する工程:

1. **請求先と対象期間を聞く** — 顧客スラッグ（`docs/clients/README.md` の対応表から引く）と請求月
2. **契約書から条件を読む** — その顧客の `02_契約・見積/` にある契約条件まとめを参照。月額固定か実績精算か、締め・支払サイト、源泉徴収の扱い、宛名の正式表記
3. **明細を組む** — 固定報酬／実費（日当・交通費）／スポット案件を分ける
4. **インボイス要件の自己検品** — 登録番号・取引年月日・税率ごとの区分・消費税額・宛名の6点が入っているか。**端数処理は税率ごとに合計に対して1回だけ**（明細ごとの端数処理は不可）
5. **検算を出力** — 明細合計と税額を Python で再計算して表示（`feedback_finance_sheet_verification` の規律を請求書にも適用）
6. **HTML → Chrome headless で PDF → デスクトップにもコピー**（既存の見積・レポートと同じ流儀）
7. **台帳に1行追記**

### スキルに内蔵したい判断（今回つまずいた3点）

1. **固定か実績精算かの読み分け** — 「月額◯円を支給し、◯時間・時給◯円での稼働を前提とする」は**固定**。時給×時間が月額と一致していれば算出根拠にすぎない。加えて「ズレたら契約金額を見直す」と書いてあれば月々精算ではない、と断定できる
2. **源泉徴収** — 対象は**個人**への支払い。**法人への支払いは原則不要**。契約書に控除条項があっても個人向けひな型の流用である場合が多いので、法人取引なら控除なしの総額で出し、先方経理と突き合わせる
3. **宛名の表記** — 契約書本文の表記が正（例: ファイア**ー**プレイス。ファイヤーではない）。社名違いは経理で差し戻される定番

### 横展開の対象

契約書ベースで継続請求が発生する顧客が複数ある。スキル化すれば全部に効く。
`osaka-kyoso-lab`（月額30万・2027年2月まで）／`mutsubi`（月額88万＋前受金プール）／`clavis-partners`／`hare`／その他スポット。

→ 既存候補 **#14「請求チェックの半自動化」**（入金確認側）と対になる。#18で発行側を作り、台帳を共通化すれば #14 が自然に成立する。

## 7. 税理士への月次提出（領収書＋カード明細）の設計シード（2026-09-03 起票）

> **この項目は別セッションで着手する。**起票だけしてある。着手時はまず [docs/company/invoice-constants.md](../company/invoice-constants.md) の
> 「請求のまわり方（4つの箱と、その関係）」を読むこと。請求側で分かった前提がそのまま効く。

### いま何をやっているか（阿部さんヒアリング前の理解・要確認）

- 領収書の**紙**を溜めておき、月次で税理士に渡している
- **決済したカードの明細を印刷**して、それも一緒に渡している
- 渡し方は手渡し（郵送？）。頻度は月1回

### 着手時に必ず聞くこと（ここが決まらないと設計できない）

1. **税理士側が受け入れられる形式** — ここが最大の制約。PDF一括／科目別フォルダ／会計ソフト連携（何を使っているか）／紙のまま、のどれか。**先に税理士に確認してもらう**
2. **対象範囲** — 領収書だけか、請求書（買掛側）・通帳・給与関係まで含むか
3. **枚数の実感** — 月何枚か（10枚と200枚で設計が変わる）
4. **カード** — 何枚のカードか。明細はWeb明細をDLできるか、紙で届くか
5. **電子帳簿保存法の扱い** — 現状どう運用しているか（スキャン保存の要件を満たす必要があるか）。ここは**税理士の指示が正**

### 請求側の作業で分かっている前提（そのまま使える）

- **Googleドライブのデスクトップ同期がローカルに見えている**
  `~/Library/CloudStorage/GoogleDrive-tabe@balencer.jp/マイドライブ/...`
  → **同期フォルダに新規ファイルをcpすればDriveに上がる**。API不要。領収書PDFの格納はこの手が使える
- ただし**同期フォルダ内の既存ファイルの上書きはハーネスのガードで止まる**（許可を得ても止まった）。
  既存の会計ブックを更新する設計にすると詰まる。**新規ファイルを作る設計にする**
- **Googleスプレッドシートはセルを書き込めない**（読み取りのみ）。台帳をスプレッドシートに置く設計は避ける
- 経理まわりの原則として **「読むのは自動、書くのは人」** で合意している（2026-09-03）。
  提出物の生成までをClaudeがやり、台帳への記入・提出は人、が既定線

### 筋がよさそうな方向（叩き台・確定ではない）

1. 領収書はスマホで撮る → 特定フォルダに入れる → OCRで日付・金額・支払先・科目候補を抽出 → 月次でPDFに束ねて索引を付ける
   - OCRは Gemini でPhase0実証した前例あり（NAILIT案件・`project_sales_dashboard_client`）
2. カード明細はWeb明細のCSV/PDFをDL → 領収書との突合表を出す（**突合こそが税理士の手間**の可能性が高い）
3. 出口は「月次フォルダ1つ（PDF＋突合表）」にして、Driveに置いて共有リンクを渡す
