# 開発指示プロンプトの型 — 「利用者ごとに最適化」＋セルフチェック運用

出典: 2026-09-03 HASSIN様定例のあと、加藤（梨紗）さんが Claude と詰めた対話。ネクサスグループHD／HASSIN 制作システムの開発指示に使うために作られたが、**案件非依存の汎用型**として横展開できる。
関連: [`../clients/nexus-group/事業会社/hassin/01_制作システム/`](../clients/nexus-group/事業会社/hassin/01_制作システム/)

## 2026-09-03 決まったこと

**却下した書き方**: 「スマホファーストのレスポンシブデザインで作って」
→ 全画面が一律スマホ優先になる。制作チームはPC・現場はスマホという**画面ごとに主利用者が違うシステム**では誤った最適化になる。

**採用した書き方**: 「**利用者ごとに最適化**」＋「**セルフチェック → ベスト案1本 → OK後に実装**」
- 画面ごとに主利用者・利用環境を判定させ、最適化対象を切り替える
- 主利用者が指定されていない場合は**確認を挟まず自分で判断し、判断理由を一言添えさせる**（往復を減らす）
- 修正点を逐一やり取りせず、**セルフチェック済みの完成度の高い1案**を出させる（複数案を並べさせない）
- HTMLモックアップを先に出し、OKが出たらそれを本実装に反映する

狙いは**最小のコミュニケーションで良いアウトプットを出す**こと。指示側が重なり・崩れの指摘役をやらない。

## 汎用テンプレート（下3つの【　】欄だけ差し替えて使う）

```
【最重要要件：利用者に応じたUI最適化】
このシステムは画面によって主な利用者・利用環境が異なる前提で設計する。
画面ごとに「誰が」「どんな環境で」使うかを判断し、その環境に最適化すること。

- PC利用が前提の画面（管理・運用・確認系など情報量が多い画面に多い）
  → 情報量・操作効率を優先したPC最適化のUIとする。
  　スマホ・タブレットは崩れない程度でよく、優先度は低い。

- スマホ利用が前提の画面（現場・外出先・一般ユーザー向けなど）
  → 片手操作・タップ領域44px以上・縦積みレイアウトを基準に
  　スマホ最適化のUIとする。PC表示は崩れない程度でよく、優先度は低い。

※ どちらが主かの指定がない場合は、画面の目的・想定ユーザーから
  自分で判断し、判断理由を一言添えること（確認は挟まない）。

【進め方：セルフチェック→ベスト案提示→実装】
1. まずHTMLの静的モックアップ（プロトタイプ）を作成する。
2. 完成後、以下を自分でチェックしてから提示する。
   - 対象デバイス幅（PC想定なら1280/1440px、スマホ想定なら375/390/430px）で
     文字・要素の重なり、はみ出し、干渉がないか
   - ボタン・リンクの押しやすさ、フォームの入力しやすさ
   - 崩れや違和感があれば、提示前に自分で修正しておく
3. 修正点を逐一確認するのではなく、
   「この画面ならこの形がベスト」と判断した完成度の高い1案を出力する。
   　複数パターンを並べる必要はない。
4. OKが出たら、そのモックアップをそのまま本実装に反映する。

【画面の目的】
（ここに画面の目的を記載）

【想定利用者】
（ここに利用者と利用シーンを記載）

【必要な要素・入力項目】
（ここに表示・入力項目を記載）
```

## 効いている指示のコツ（加藤さんの実践知）

- 「**アプリっぽく作って**」と指示すると機能的なUIが返ってきやすい（下部固定CTA・カード型リスト・タブバー等）
- 参考UIを名指しする（例: ホットペッパー／ぐるなびのフローティング条件バー）と精度が上がる
- 入力項目が多い画面は**ウィザード（段階分割）**を検討させる

## 宿題

- 使用頻度が上がるなら**スキル化**する（`.claude/skills/` へ。→ [[feedback_repetition_to_skill_automation]] の3回ルール）。まずはこのファイルをコピー元として運用し、回数が溜まってから昇格させる
- クライアント側にも渡す場合は Notion のテンプレページに置く選択肢あり（加藤さん案）
