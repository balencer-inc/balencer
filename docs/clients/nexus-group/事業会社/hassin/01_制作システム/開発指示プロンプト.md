# 制作システム 開発指示プロンプト（HASSIN版）

梶原さん／Claude に画面開発を依頼するときの定型文。**下3つの【　】欄だけ差し替えて使う**。
汎用版と成り立ちは [`docs/_knowledge/dev-ui-prompt-per-user.md`](../../../../../_knowledge/dev-ui-prompt-per-user.md)。

> **前提（言い過ぎないための注意）**: 制作チームはPC・現場（店舗側）はスマホ。**全画面をスマホファーストにしない**。画面ごとに主利用者を判定して最適化する。

```
【最重要要件：利用者に応じたUI最適化】
このシステムは画面によって主な利用者が異なる。
それぞれの利用環境に最適化して設計・実装すること。

- 制作チームが使う画面（例：案件管理、ダッシュボード、単価マスター等）
  → PCでの利用が前提。情報量・操作性を優先したPC最適化のUIとする。
  　タブレット・スマホ対応は崩れない程度でよく、優先度は低い。

- 現場（店舗側）が使う画面（例：依頼受付、進捗確認等）
  → スマホでの利用が前提。片手操作・タップ領域44px以上・
  　縦積みレイアウトを基準にスマホ最適化のUIとする。
  　PC表示は崩れない程度でよく、優先度は低い。

※ 対象がどちらか分からない場合は、指示側に確認せず
  画面の用途・想定ユーザーから自分で判断し、判断理由を一言添えること。

【進め方：セルフチェック→ベスト案提示→実装】
1. まずHTMLの静的モックアップ（プロトタイプ）を作成する。
2. 完成後、以下を自分でチェックしてから提示すること。
   - 対象デバイス幅（PC想定なら1280/1440px、スマホ想定なら375/390/430px）で
     文字・要素の重なり、はみ出し、干渉がないか
   - ボタンやリンクの押しやすさ、フォームの入力しやすさ
   - 崩れや違和感があれば、提示前に自分で修正しておく
3. 修正点をこちらに逐一確認するのではなく、
   「この画面ならこの形がベストと判断した」という完成度の高い1案を出力すること。
   　複数パターンを並べる必要はない。
4. こちらがOKを出したら、そのモックアップをそのまま本実装に反映する。

【画面の目的】
（例：店舗担当者がスマホから制作依頼を提出する画面）

【想定利用者】
（例：店舗側スタッフ）

【必要な要素・入力項目】
（例：案件種別、希望納期、印刷オプション、参考画像添付 など）
```

## この画面はどちら向きか（早見表）

| 画面 | 主利用者 | 最適化 |
|---|---|---|
| 依頼受付 | 店舗側スタッフ | **スマホ**（最優先。現状「絶望的に見にくい」） |
| 進捗確認 | 店舗側スタッフ | スマホ |
| 個人ダッシュボード | 制作チーム | PC（スマホ版は改良済み） |
| 制作部全体ダッシュボード | 制作チーム | PC |
| 案件一覧 | 制作チーム | PC |
| 作業報告書（日報） | 制作チーム | PC |
| 請求書発行・単価マスター | 制作チーム | PC |
| アーカイブ（過去制作物ギャラリー） | 制作チーム＋店舗側 | 両対応（閲覧はスマホも想定） |

## 依頼受付をやるときの追加指示

- 参考UI: ホットペッパー／ぐるなび系の**フローティング条件バー**（画面下部固定のCTA／絞り込みバー）
- 入力項目が多いので**ウィザード（段階分割）形式**を検討させる
- 「**アプリっぽく作って**」を添えると機能的なUIが返ってきやすい
