株式会社東洋様 機関紙スマホ配信 想定要件定義 v0

性格: 先方ヒアリング前の仮説ベースの要件定義。いただいた相談文4行から文脈を読み、実装に必要なものを先回りで起こしたもの。 確定要件ではなく、これを叩き台にして「合っている／違う」を潰すための材料。 作成 2026-08-29 ／ 社内作成物（第3章までは先方に見せられる粒度、第9章は社内向け）

1. 相談文から読み取った文脈

いただいた一文は4行だが、業種の型から埋められる前提がかなりある。以下は推定であり未確認。

# 読み取り 根拠
推定1 現状は組版済みPDFをサイトに1つ置いているだけ。スマホだとピンチズームが必要で読まれていない 「スマホビューに変換」という言い方は、変換前の何か（＝紙面PDF）が既にあることを示す
推定2 機関紙は継続発行物。月刊〜季刊で、今後も出続ける 機関紙という語自体が定期刊行を含む。単発なら「変換してほしい」で終わり、「仕組み」とは言わない
推定3 本当に欲しいのは変換そのものではなく、毎号それが回る状態 「変換して」「配置し」「配信する」を並べたうえで「仕組みのアプリ」と締めている。3工程を毎号繰り返す前提の言い回し
推定4 運用するのは公的機関の職員。非エンジニアで、担当は数年で異動する 公的機関の内部運用の通例。属人化した手順は引き継がれず、いずれ止まる
推定5 配信先Webサイトは既存のものがあり、そこに載せる 「WEBサイトに配置し」＝新規サイト構築ではなく既存への組み込み
推定6 紙・PDFをやめるつもりはない。Web版は追加チャネル 公的機関は高齢読者を切れない。紙面PDFの併存は前提と見るべき

この案件の本質（推定3から）

PDFを綺麗に見せる案件ではなく、紙のワークフローに1工程足すだけで、Webの読み物が毎号ひとりでに立ち上がる状態をつくる案件。

ここを外すと、初号だけ立派で2号目から誰も更新しない典型的な失敗になる。要件の重心は見た目ではなく入稿から公開までの導線に置く。

3. 機能要件

3-1. 読者側（スマホで読む人）

ID 要件 優先 想定人日
R-01 号の目次ページ（表紙画像＋記事一覧＋発行日） Must 2
R-02 記事詳細（縦スクロール／文字サイズ変更／行間調整） Must 3
R-03 バックナンバー一覧（年度別・号数順） Must 1.5
R-04 カテゴリ・タグでの絞り込み Must 1
R-05 全文検索（号をまたいで探せる） Must 1.5
R-06 元PDFのダウンロード導線 Must 0.5
R-07 共有（LINE・X・Facebook・URLコピー） Must 0.5
R-08 前後の記事送り・関連記事 Must 0.5
R-09 音声読み上げボタン Should 1.5
R-10 新着のお知らせ購読（メール／LINE） Should 3

R-06を落とさない。紙面レイアウトで読みたい層と印刷したい層が必ず残る。既存読者を切らないための保険であり、公的機関では説明責任にもなる。

3-2. 管理側（職員が毎号回す）

ID 要件 優先 想定人日
A-01 号の作成・PDF（＋元データ）アップロード Must 1.5
A-02 変換の実行と進捗表示 Must 2
A-03 記事校閲エディタ（本文修正・見出し・画像差し替え・代替テキスト入力・カテゴリ付与・記事の分割/結合・並び替え） Must 8
A-04 スマホ実寸プレビュー Must 1
A-05 予約公開（発行日に合わせて自動公開） Must 1
A-06 権限管理（編集者／承認者の2段階） Must 1
A-07 配信の実行（メール・LINE・SNS） Should 3
A-08 アクセス解析（どの記事が何回読まれたか） Should 2
A-09 バックナンバー一括取り込み Should 2

A-08は機能というより先方の武器。公的機関は予算の効果を説明する必要があり、紙では「何部配った」しか言えない。「どの記事が何人に読まれたか」が出せると、Web版を続ける理由が内部で立つ。提案の柱に使える。

A-03が単一機能で最大の8人日。ここが本体だと最初に握っておく。

3-3. 変換パイプライン（②の中身）

工程 中身 想定人日
抽出 PDFからテキスト・画像・座標を取得。段組と回り込みを座標情報から復元 3
構造化 Claude APIで記事の境界判定、見出し／リード／本文／キャプションの役割付与、代替テキスト案の生成 4
整形 HTML化、画像の切り出しとリサイズ、見出し階層の正規化 3
精度チューニング 実際の号で回して評価・調整 3
計 13

元データがInDesign（IDML／タグ付きテキスト）で入手できるかで精度が段違いに変わる。段落スタイル情報がそのまま使えるため、構造化の推測がほぼ不要になる。確認事項Aで最初に聞くべき理由がこれ。PDFのみ、かつスキャン画像だと工数もリスクも跳ねる。

5. 非機能要件

ID 要件 備考
N-01 JIS X 8341-3:2016 AA準拠（コントラスト比・キーボード操作・代替テキスト・見出し構造・200%拡大時の可読性） 公的機関案件では要求される前提で設計する。後から言われると作り直し

6. 想定スコープ外（明示して握る）

  • 機関紙そのものの企画・執筆・組版（紙面制作は現行体制のまま）
  • ネイティブアプリ（App Store／Google Play への申請・審査）。「アプリ」の語はあるが、Web＋PWAで要件は満たせる想定。ストア配布が必須なら別要件
  • 会員限定・ログイン必須の閲覧制限
  • 多言語対応
  • 既存Webサイト全体のリニューアル

8. 推定が外れたときにどこが動くか

外れる推定 影響
推定1が外れ、元データがスキャン画像PDFだけ 抽出工程がOCR前提になり、変換パイプラインが13→20人日超。精度も落ちる。最悪ケース
推定3が外れ、実は初号だけの単発制作 校閲エディタ(8)・変換パイプライン(13)・入稿まわり(A-01/02/05=4.5)が不要になり 約35人日 まで落ちる。ただし1号分の変換は人手で行う前提
推定5が外れ、公的機関の指定CMSに載せる必要がある 実装先の制約次第。触れる範囲が狭いと外部サイト＋リンク方式に変更
推定6が外れ、紙をやめてWeb一本化したい R-06の重みが下がる代わりに、アクセシビリティ要求が跳ね上がる（唯一の情報チャネルになるため）
バックナンバー移行が要求範囲に入る 号数×0.5〜1.5人日で線形に追加。50号なら+25〜75人日

9. 提案時の組み立て（社内メモ）

  • 売り物は変換ではなく仕組み。「PDFを綺麗にします」で出すと相見積で値段勝負になる。「毎号ひとりでに立ち上がる状態」を売る
  • A-08（アクセス解析）を提案の柱に置く。紙では出せなかった数字が出ることが、先方の担当者が内部を説得する材料になる。ここが受注理由になりうる
  • AA対応を先に持ち出す。公的機関案件で後出しされる筆頭であり、こちらから設計段階で織り込んでいると示せると信頼が跳ねる。相見積の相手が触れていなければ差がつく
  • 段階提案にする。第1段階=新規号から運用が回る状態（約60人日）、第2段階=バックナンバー移行（AIで圧縮）、第3段階=配信チャネル拡張。一括1,000万の見積は公的機関の予算では通らない
  • 変換のAI圧縮は実物1号でPoCを回すまで約束しない
