0. 結論

理由は3つ。

  1. 設計案の第9章に「本運用はバレンサーの参画を前提とする。第三者が入らない形での実施は想定しない」と明記されている。先方が自らバレンサーを構造の中心に置いた。これは月額の増額根拠として最も強い形で、こちらから取りに行った関与ではない。
  2. 一方で、この設計はバレンサーの工数を一切見積もっていない。全員必須45分ヒアリング＋所見の戻しは、1人あたり実工数で約1.5時間。仮に20名なら半期ごとに30時間が乗る。既存の月額に飲み込むと半期ごとに大きな持ち出しが出て、2期目で必ず続かなくなる。
  3. この運用は人事制度ではなく、MVV（真・善・美）を日々の判断に落とす実装そのもの。すでに走っている社内報・課題図書セッションと一続きにできる。単発の制度支援で終わらせず、組織開発の本線に乗せられる。

ただし、そのまま「はい」とは言わない。 設計案には運用初期に折れる箇所が明確にあり、そこを潰す提案を持って行くこと自体が、こちらの価値の証明になる（→ 2章）。

1. 何が起きているか

  • ユニット（DEV／SI／バックオフィス）に評価を委ね、会社は口を出さない方針。その結果ユニット間に温度差が生まれ、一体感が損なわれている
  • 3月に利益分配金のルールを変更し、査定軸を「情報流通／教育／決断／会社ルールの遵守」に刷新。全てに通底するのが「主体性」
  • 主体性を伸ばす仕組みが要る、という問題意識から今回の相談に至った
  • 管理者側は、期待を言語化できない・言うと業務指示になる・言われた側の希望に応えられない、という三重の詰まりを抱えている
  • 8/31の面談は決着せず。管理者の生の悩みが出たところまで
  • その後、藤江さんから設計案が届いた

同日に議事録と設計案が並んでいる。 議論の熱が冷めないうちに形にされたということで、先方の本気度は高いと読む。

2. 設計案の評価

効いている設計（触らない）

① 上長が書く相手を、本人ではなくバレンサーにした

「個人宛に期待を書けない」という詰まりを、読み手を変えるだけで解いている。評価語のまま書いてよい、と明示したのも正しい。管理者の心理的ハードルを下げる一手として、これ以上のものはない。

② カウンター（場面 × 選択）への落とし込み

この設計の白眉。「〈この場面〉のとき〈A〉より〈B〉を選ぶ」に固定することで、人格を指さず、会社が機会を与える約束も発生しない。前回の最大の懸念だった「言ったけど何も変わらなかった」を、根性論でなく構造で回避している。

③ 藤江さんの確認を事前承認のゲートにしない

差し戻すと管理者は「通る書き方」を学習し、書かれる内容が本人でなく社長向きに歪む、という読みは正確。見立ての当否を半期ごとに蓄積して精度を上げる、という設計に置き換えたのも良い。

運用初期に折れる箇所

① 週次ログの提出先が Unit管理者になっている（最重要）

設計案は「評価に使わない」と宣言しながら、迷いとつまずきを毎週上長に提出させる。管理者側には「内容を評価しない・薄さを指摘しない・督促だけしてよい」と縛りをかけているが、書く側から見れば読み手は上長のままで、この縛りは見えない。

結果、3週目あたりから当たり障りのない記述に寄る。「迷いは毎週あるので嘘をつく必要がない」という前提は、読み手が上長でないときにだけ成立する。

② ログに反応が返らない構造になっている

管理者は評価も指摘もしてはいけない。つまり本人から見ると、毎週書いても何も返ってこない。週次の内省ログは、日本の中小企業で最も枯れやすい仕組みで、反応がないものは4週で止まる。SI Dailyが回っているのは業務報告だからで、内省ログとは別物として扱ったほうがいい。

③ ヒアリング工数が設計に入っていない

全員必須45分。準備15分＋所見と待ち方の作成30分を足すと1人1.5時間。ここは案件の芯であり、同時に無償で飲むと続かなくなる箇所。人数の確認が見積の全て。

④ 「テーマ名のみ公開」では、当初の目的に効かない

名詞句1行を全社に貼っても、相互支援は起きにくい。元の狙いはユニット間の温度差と一体感だったはずで、テーマ名の一覧共有では届かない。テーマを本人の言葉で語る場が要る。

⑤ バックオフィスの負担への回答がない

前回、展開方法の議論でバックオフィスの負担が懸念に挙がっている。設計案は月1面談への差し込みで済ませているが、管理者側の記入と受け取りの負担は他ユニットと同じ量が乗る。

⑥ 制度の名称が未決のまま（8章の1）

名前が評価っぽく聞こえた瞬間、全体が評価制度に見える。ここは最後の詰めではなく、最初に決める項目。

3. 当初の狙いから落ちたもの

藤江さんが最初に出した3行はこうだった。

  1. 会社・Unitとして君に期待していること、望んでいることを伝える
  2. それに関係してもしなくてもいい。今興味があること、これからやりたいことを宣言する
  3. 2をご本人の興味情報として社内で公表する

設計案では、1は「テーマ」として残り、3は「テーマ名のみ公開」に縮んだ。2の「やりたいことの宣言」は、業務・配置の希望として従来の1on1に分離され、実質的に落ちている。

落とした判断自体は理にかなっている。管理側が応えられない希望を背負わないための分離で、前回の議論を正しく反映した結果だ。

ただし、落ちたことによって残るものがある。本人から見ると、期待は受け取るが、自分の希望を出す場は増えていない。相互理解ではなく一方通行に見える。前回の面談で「期待を伝えるなら本人の考えも聞くべき（フェア）」と申し上げたのは、まさにここ。

戻し方の案：業務・配置の希望（応える約束が要るもの）と、ありたい姿・3年後5年後の方向（約束が要らないもの）を分ける。後者はヒアリングの中で扱い、本人が出してよいと言った範囲だけをテーマと一緒に社内に出す。約束を背負わずに、双方向を回復できる。

4. バレンサーの役割定義（ここを最初に文書化する）

この運用でバレンサーは、社員一人ひとりの本音を預かる立場になる。線引きを最初に紙にしないと、必ず揉める。

扱う扱わない
ありたい姿、テーマ、カウンター人事評価、査定、利益分配金への意見
判断の迷い、つまずきの言語化担当変更・アサイン・待遇の要望の取り次ぎ
見立てと実感のズレの検証個人間のトラブルの裁定
管理者への「待ち方」の提示退職相談の受け皿

会社に返すもの：テーマ、カウンター、一行の所見、待ち方。

会社に返さないもの：相談枠で聞いた本音と迷い。ただし、本人の安全に関わる内容と、制度そのものが機能していないサインは例外とし、その例外があることを本人への説明時に先に伝える。

中立性については、報酬を会社から受け取っている以上「完全な中立」は名乗れない。名乗るべきは「評価しない立場」であって中立ではない。ここを言い換えずに初回説明で正直に言うほうが、結果として信用される。

5. 案件としての形

段階の切り方

段階内容バレンサーの動き
Phase 0（9月）設計の確定折れる箇所の修正、制度の命名、本人配布資料、管理者の記入フォーマット、Slackワークフロー、説明会の台本
Phase 1（半期頭・10月想定）立ち上げ管理者3名の読み合わせ60分ファシリ、全員ヒアリング45分×N、テーマとカウンターの決定、管理者と藤江さんへの戻し
Phase 2（半期中・毎月）運用伴走ログの温度チェック、テーマの置き直し、相談枠、管理者へのフィードバック、月次差し込みの設計
Phase 3（半期末）振り返りと接続振り返り設計、全体会での共有ファシリ、管理者の見立て精度レポート、次期テーマへの引き継ぎ

値付けの考え方（金額は未確定・阿部さん判断）

  • Phase 0 と Phase 1 は PROJECT として別建て。ここに工数の山があり、月額に飲み込むと持ち出しになる
  • Phase 2 と Phase 3 は月額（既存契約の増額、または CONSULT／PARTNER）
  • Phase 1 は人数で動くため、1名あたりの単価構造で組む（ヒアリング＋所見＋戻しで1.5時間相当）。人数が確定するまで総額を出さない

注意：今期は営業利益率でDEVが10%程度、SIはマイナスと社内共有されている。総額を先に置くと止まる可能性がある。Phase 0 を小さく切って先に動かし、Phase 1 の見積は人数確定後に出すのが安全。

6. ここから膨らむ筋（確度順）

① 社内報との接続（確度：高・追加コスト小）

テーマとカウンターの実例を社内報のコンテンツにする。すでに運営している枠の拡張で、当初の目的だった相互理解に最も直接効く。テーマ名の一覧共有が飾りになる問題（2章④）の解でもある。

② MVV浸透の本線（確度：高）

週次ログで真・善・美のどれに引っかかったかを毎週選ばせる設計は、MVV浸透の実装そのもの。課題図書セッションと合わせて「MVVを日々の判断の分岐点に置く」一本の線として組み直せる。

③ 管理者（ユニット長）のマネジメント支援（確度：中〜高）

期待を言語化できない、言葉が強くなる、なだめ役と怒り役を交代できない。これは制度でなく管理者側の技術の課題で、この運用を回すほど輪郭がはっきりする。1on1の型づくりや管理職向けの伴走が素直に続く。

④ 職務記述書・キャリアラダー（確度：中）

面談でSIの沼田さんから「職務内容書のような土台があると、キャリア開発の道筋が線になる」という発言が出ている。DEVは業務ごとの客単価でステップを説明できるが、SIは説明できていない。実需があり、名指しで要望が出ている。

⑤ SIの情報流通と収益（確度：中・金額は最大）

SIは営業サイドの情報が入らず、数字目標の周知もできていない。そしてSIの利益がマイナス。新しい査定軸の第1項目が「情報流通」であることとも符合する。これは人事の話ではなく事業と業務基盤の話で、踏み込めれば案件規模は最も大きい。ただし今回の相談の枠外なので、成長テーマ運用を回す中で見えたものとして半期末に出すのが順番として正しい。

7. 受ける前に確認すること

  1. ヒアリング対象は何名か。見積の全てがここで決まる
  2. 費用の想定があるか。設計案は参画を前提としているが、費用の記述がない。既存契約の枠内か、追加かを最初に握る
  3. 半期の区切り（現行の期に合わせるか、10月開始か）。設計案8章の未決事項
  4. 週次ログの提出先を変える余地があるか（2章①）。ここは譲れない論点として持って行く
  5. 管理者3名は誰か（DEV／SI／バックオフィス）。書く負担を負うのはこの3名
  6. 議事録上の人名の確認。文字起こしに「藤井さん」表記が混在しており、藤江さんを指すと思われる。また「阿部」が複数の文脈で出ており、当社の阿部と先方の方が混在している可能性がある。資料化の前に整理が必要

8. 次回MTGの出し方

前回は決着しなかった。次回は決めさせる設計にする。

対案を並べるのではなく、設計案を1枚に整理し直したものと、決めるべき論点を3つだけ持って行く。社長案を否定する形は取らない。骨格は良く、折れる箇所だけを直す、という立て方にする。

決めてもらう3点

  1. 週次ログの提出先 — 管理者／バレンサー／本人のみ。「評価に使わない」と両立するのはどれか
  2. やりたいことの宣言を戻すか — 当初の2と3。戻すなら、業務希望と切り分けてヒアリングの中で扱う
  3. 対象と開始時期 — 全員一斉か、開始は10月か期に合わせるか

あわせて置く

  • 制度の名称案（3つ程度）
  • バレンサーの役割と、扱わないことの線引き（4章）
  • 段階の切り方と、費用が発生する範囲（5章）

この場でPhase 0の合意まで取る。 設計を確定させる作業自体を先に有償の枠にすることで、以降の話が「相談」から「案件」に変わる。
