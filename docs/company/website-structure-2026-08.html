バレンサー コーポレートサイト｜構造とAIO実装の決定

決定日：2026年8月24日 文言の正本：website-copy-master.md（このファイルは構造・実装・更新責任の正本） 本番環境：WordPress + Elementor（balencer.jp）

決めたこと：HPはコンテンツを増やす場所ではなく、確信を与える記録にする。思想と現場はnoteに書き、HPは会社の定義を持つ。コーポレートサイトでブログは運用しない。更新されないことは欠点ではなく仕様とする。

1. 3層構造

13ページの設計（文言マスター §1）は変えない。性質と更新責任を3層に分けて、どこを更新しないかを決める。

層 ページ 性質 更新の頻度と責任
動かない記録（11ページ） / /about/ /about/philosophy/ /service/ ＋4領域 /plan/ /recruit/ /contact/ 会社の定義。AIと、商談前に確認する人が読む ほぼゼロ。docs/company/ の正本を変えた時だけ
資産の記録（1ページ＋個別） /project/（事例） 会社が何をやったか。実体をHPに持つ 案件が終わったら追加（年に数回）
流れるもの（1ページ） /insight/（読みもの） 実体を持たない。noteの索引 note側の更新のみ（自動取得）

商品LP群（/hojokin/ /notion/ /keiei/ 等）は別レイヤー。金額を持つのはここだけで、コーポレート本体は非掲載を維持する。

2. /insight/ を索引化する

変更点

変更前 変更後
記事の実体 HP（WordPress投稿） note（阿部貴之名義）
/insight/ の中身 記事一覧＋本文 note記事のタイトル・日付・冒頭1行を並べ、noteへ送る
約束していること 毎月、現場から得た知見を書く 思想と現場はnoteに書いている
更新作業 記事執筆＋投稿 なし（RSSで自動）

コピーは文言マスター §13 と §3.11 に反映済み。

実装

noteのRSS（https://note.com/<アカウント>/rss）をWordPress側で取り込み、カード表示してnoteへ外部リンクする。

  • 実装場所は functions.php の fetch_feed()、またはElementorのカスタムHTMLウィジェット。キャッシュは12時間
  • 表示するのはタイトル・公開日・冒頭1行まで。本文はHPに置かない
  • RSSが不安定な場合のフォールバックは月1回の手貼り（10分）。それでも本文は置かない

ここでやらないこと

  • noteの記事をHPに転載・要約しない。 正本が二重化して、どちらが最新か分からなくなる（docs/ の運用原則と同じ）
  • カテゴリをHP側で作り直さない。noteのハッシュタグに寄せる
  • SNSの埋め込みタイムラインを置かない（重くなるだけで読まれない）
  • 更新頻度を上げるための記事を書かない

3. 事例 /project/ だけは実体をHPに持つ

理由：AIと、商談前の人が「この会社は何をやったか」を引く唯一の場所。noteの流れるコンテンツでは代替できない。会社の資産なので、個人名義のnoteに置くべきものでもない。

書式を揃える（社名は伏せて業種表記。伏せても構造で機能する）。

  1. 業種・規模・立場（承継2代目など）
  2. 相談時の状態（何に困っていたか）
  3. 横断した領域（4領域のどれをどう組んだか）
  4. やったこと（設計・ディレクション・実装の切り分け）
  5. 変化（数字＋人や空気の質的変化。両方入れる）
  6. 期間と関与範囲

4. AIから読める形にする（構造化データ）

今の13ページは人間向けの構成としては機能するが、AIから見ると「バレンサーとは何か」が / /about/ /service/ に分散している。ページを増やさず、JSON-LDを足すだけで効く。

入れる場所 型 効果
全ページ共通（head） Organization 会社が1つの実体として認識される
/about/ 会社概要 Organization の詳細（設立・所在地・代表） 会社概要の事実がそのまま取られる
/about/ 代表 Person（阿部貴之）＋ worksFor → Organization noteの阿部貴之とバレンサーが紐づく
/service/ 4領域 Service（provider → Organization） 何を提供する会社かが取れる
/project/ 事例 Article（about → Service） 実績が取れる
/contact/ ContactPoint 問い合わせ手段が取れる

一番効くのは sameAs

Organization の sameAs に note・YouTube・X・Facebook・LinkedIn のURLを列挙する。 そして Person（阿部貴之）側にも sameAs でnoteとXを入れ、worksFor でバレンサーを指す。両方向で結ぶ。

これを入れないと、noteで積んだ信用が阿部貴之個人にしか紐づかず、会社に戻ってこない。逆に入れておけば、noteが伸びるほど会社の実体が濃くなる。

思想を個人名義で発信しながら会社の資産にするための技術的な要はここ1点。人生設計に書いた「20年後は統括側に回る／緩やかな生態系そのものが価値になる」構想と整合させるためにも、個人と会社を切り離さずに結んでおく。

実装

JSON-LDを1ブロック貼るだけ。Elementorでもテーマのheaderかコードスニペットのプラグインでheadに挿入できる。プラグインの自動生成（Yoast等）に任せると sameAs が抜けるので、手で書いて入れる。

5. 実装の順番

順 やること 目安 なぜこの順か
1 Organization ＋ Person ＋ sameAs のJSON-LD 半日 一番効く。 noteの本番運用が始まる前に入れる（記事が増えてから紐づけるより、最初から紐づいている方が素直）
2 /insight/ の索引化＋コピー差し替え 半日 noteアカウントの方針が決まってから
3 Service のJSON-LD（4ページ） 半日 領域ページの文言が確定済みなのですぐ入る
4 /project/ の書式統一＋Article JSON-LD 事例が揃ってから 中身が先。枠だけ作らない

1は note の運用開始と独立して進められる。素材（生声）が揃うのを待たずに着手できる唯一の工程。

6. 保留（阿部さんの判断待ち）

/plan/ に「料金の考え方」を書くか

金額そのものではなく、構造（月額制／初回6ヶ月／以降3ヶ月更新／末日締め翌月末払い／制作・開発はPROJECTとして別見積）を書くかどうか。

  • 書く場合：問い合わせの質が上がる。AIに価格帯を聞かれた時にも答えが返る
  • 書かない場合：商談まで一切分からない。現行の設計はこちら（正本§9・数字を先に固定しない）

noteのアカウント名義

  • 阿部貴之個人名義のまま（推奨）：思想は人に宿る。会社名義の思想発信は薄くなる。会社への紐づけは §4 の sameAs と worksFor で担保する
  • バレンサー公式も別に持つ：更新責任が増えるので、個人名義が回り始めてから判断する

7. この決定が前提にしていること

  • 実際の受注経路は紹介・休眠掘り起こし・対面（sales-strategy-2026.md）。HPはマス集客の装置ではなく、紹介を受けた人が検索して見に来たときに信頼できると判断できることが役割（文言マスター §0）
  • したがってHPの評価軸は流入数ではない。商談前に読んだ人が確信を持てるか、AIが会社を一意に説明できるかの2つ

確度の低い前提（断定していない）

どのAIモデルがどのドメインをどれだけ引用するか、AI検索経由の実際の流入量については実測データを持っていない。判断を変えるほど重要になった時点で調べる。§4の構造化データは、その結果に関係なく効く（機械可読の会社情報を持つこと自体が損にならない）ため先に入れる。
