## 1. 最初に決めること — 全部を一度に売らない

A〜Hを1本のパッケージで全部やろうとすると、中小企業が払える帯を超える。数千万規模のデータ基盤整備から入って予算と忍耐が切れる、というのが調査に出ていた典型的な失敗そのものになる。

かといって8つをバラバラのメニューにすると、今と同じ（案件ごとに形が違う）に戻る。

**採る構造はこれ。**

> **最小の1周を90日で回し、残りは継続契約の中で埋める。**
> 埋まっていないブロックが、そのまま次の提案になる。

この形なら、①価格が中小企業の帯に収まる ②毎回同じ工程なので型が溜まる ③継続への接続が構造として組み込まれる、の3つが同時に成立する。

## 2. ブロックごとのサービス定義

各ブロックについて、**何を渡すか・どう作るか・どこで終わりか**を決める。終わりの判定基準がないブロックは売れない（終われないから）。

### A｜会社の定義

- **渡すもの**: 存在意義・目指す姿・大切にする価値観と、それが日々の判断でどう使われるかの言葉
- **作り方**: 経営者インタビュー → 社員対話（少人数×複数回） → 言語化 → 社員が自分の言葉で言える状態まで
- **所要**: 全社浸透まで1〜3ヶ月。**90日の中では経営者の判断基準を言語化するところまで（A簡易）**
- **終わりの判定**: 社員3人に別々に聞いて、同じ意味のことが返ってくる
- **単独で売れるか**: 売れる（MVV策定として既に売っている）

### B｜事業と商品

- **渡すもの**: 何を売るか・いくらか・何は売らないか・誰が担うかの一覧
- **作り方**: 既存の見積と請求と実績から実態を洗い出す → 経営者と突き合わせる → やらないことを決める
- **所要**: 2〜4週間
- **終わりの判定**: 現場が値引きの可否を自分で判断できる
- **単独で売れるか**: 売れない（Aがないと判断の基準が作れない）

### C｜顧客

- **渡すもの**: 顧客名簿と、関係の履歴（誰と何があったか）が1箇所にある状態
- **作り方**: 既存の台帳・メール・個人の記憶を集約 → 更新の担当と頻度を決める
- **所要**: 2〜4週間＋運用の定着
- **終わりの判定**: 担当が変わっても、前任と同じ話ができる
- **単独で売れるか**: 売れる。ただし単体だとCRM導入と区別が付かず、値段も比較される

### D｜決め方

- **渡すもの**: 誰が何を決めるか／どの会議体で／何を基準に／何はやらないか
- **作り方**: **経営会議に同席して実態を観察** → 決裁の詰まりを特定 → 権限の線を引き直す → 経営者の合意を取る
- **所要**: 2〜3ヶ月（会議の開催回数に依存する）
- **終わりの判定**: 社長決裁だったものが1つ以上、現場決裁に移っている
- **単独で売れるか**: **売れない**。同席が前提なので、継続契約の中でしか作れない

### E｜業務の型

- **渡すもの**: 対象業務の手順書と、例外の扱い
- **作り方**: 現場に張り付いて実際の作業を観察 → 手順化 → 現場に直させる
- **所要**: 1業務あたり2〜4週間
- **終わりの判定**: その業務を知らない人が、手順だけで7割できる
- **単独で売れるか**: 売れる（業務改善として）

### F｜言葉とデザインの基準

- **渡すもの**: 使う言葉／使わない言葉／見た目の基準／出す前の判定手順
- **作り方**: 既存の対外物を集めて棚卸し → ブレを特定 → 基準化 → チェックの仕組みを渡す
- **所要**: 3〜6週間
- **終わりの判定**: 別の人が作ったものを、基準だけで合否判定できる
- **単独で売れるか**: 売れる（ブランドガイドラインとして既に売っている）

### G｜記録の置き場ルール

- **渡すもの**: どこに何を置くか・命名・権限・捨て方
- **作り方**: 現状の散らばりを可視化 → 置き場を決める → 移す → ルールを渡す
- **所要**: 3〜6週間。**90日の中では対象業務まわりだけ（G最小）**
- **終わりの判定**: 新しい資料が、言わなくても正しい場所に置かれている
- **単独で売れるか**: 売れる

### H｜AIへの渡し方

- **渡すもの**: A〜Gの内容をAIが前提として読み込める形にしたものと、実際に現場で動く業務AI 1本
- **作り方**: A〜Gから必要部分を構造化 → AIに読ませる → 1業務で実運用 → 現場で精度を調整
- **所要**: 2〜4週間（A・D・Eが埋まっていれば）
- **終わりの判定**: 現場が毎日使っている
- **単独で売れるか**: **売れない。ここが一番重要。** Hだけを入れるのが、生成AIパイロットの95%が成果を出せていない状態そのもの

## 3. 単独で売れるもの・売れないもの

| | ブロック | 理由 |
|---|---|---|
| 単独で売れる | A・C・E・F・G | 既に単品で売ってきた実績がある。ただし単品だと値段を比較される |
| 単独で売れない | **B・D・H** | Bは基準（A）が要る。Dは同席が要る。HはA・D・Eが要る |

**営業での使い方**: Hだけを求められた時に、断らずに順番を示す。

> AIを入れること自体は2〜4週間でできます。ただし今の状態で入れると、動かない側に入ります。先に決め方（D）と、対象業務の手順（E）を見せてください。そこが埋まっていれば、AIは最後の2週間で載ります。

これが提案ではなく**診断**として効く。相手の会社の順番を、相手より先に整理して見せることになる。

## 4. 商品の組み方

### 入口 — 充足度診断（既存のSPOT 30万円／回で成立する）

8ブロックを4段階で採点し、1枚で返す。90日で何をやるかを、ここで決める。

| Lv | 状態 | 判定の目安 |
|---|---|---|
| 0 | ない | どこにも書かれていない |
| 1 | 個人の中 | 一人の頭の中にある。その人が抜けると消える |
| 2 | 書いてある | 文書はあるが、古い／参照されていない |
| 3 | 使われている | 参照され、更新され続けている |

- 診断の出口は**Lv0とLv1のブロック一覧**と、90日で触る1業務の決定
- これがそのまま次の提案の根拠になる（提案が意見ではなく事実になる）

### コア — 90日パッケージ（金額 未決）

**必ずこの4つ＋1をやる。順番は固定。**

| 期間 | やること | 出口 |
|---|---|---|
| Day 1〜30 | **A簡易**（経営者の判断基準を言語化）＋**D**（会議同席2〜3回で決裁の詰まりを特定） | 決め方の現在地と、触る1業務の確定 |
| Day 31〜60 | **E 1本**（最も回数の多い業務を型にする）＋**H**（その業務にAIを載せる） | 現場で動いているものが1つ |
| Day 61〜90 | 現場で回して調整＋**G最小**（その業務まわりの置き場）＋引き渡しと研修 | 顧客が自分で更新できている状態 |

**触らないもの**: B・C・F と、Aの全社浸透。これは継続で埋める。範囲を広げないことがこのパッケージの品質そのものになる。

### 継続 — CONSULT／PARTNER／EXECUTIVE（既存のまま）

- 残ったブロック（B・C・F、Aの浸透、Eの2本目以降）を埋めていく
- **埋まっていないブロックが議題になる**ので、継続の理由が毎回はっきりする
- Dは継続の中でしか完成しない（同席が要るため）。ここが継続契約の構造的な根拠になる

### PROJECT（既存のまま・見積の型だけ改める）

- Fの実装（サイト・ロゴ・撮影）、Eの複数展開、Hの本格化
- 作業量ではなく**稼働し続ける状態**への固定価格にする。見積には25%のバッファを持つ

## 5. なぜこの順番なのか

- **A・Dを先にやる理由**: 決め方が決まっていない会社に道具だけ入れると、承認が通らず現場で止まる。日本企業のコア業務AI導入率1.9%・パイロットの95%が成果なしという数字は、ほぼこの順番違いで説明がつく
- **Eを1本に絞る理由**: 中小企業が求めているのは大戦略ではなく、週単位で体験できる具体的な改善。まず小さく動くものを1つ作る
- **Hを最後にする理由**: A・D・Eが揃っていればAIは2〜4週間で載る。逆にここから始めると、載せる先がない
- **B・C・F・Gを後回しにする理由**: 90日の範囲を超えるうえ、A・Dが埋まってからのほうが速く正確に作れる

## 6. 8割共通・2割個別の内訳（このサービスの資産）

案件が終わるたびに、左側の列に還す。ここが増えることが会社の資産が増えるということ。

| 共通（毎回そのまま使う） | 個別（その会社にしかない） |
|---|---|
| 充足度診断の採点表と質問集 | 採点の結果 |
| ブロックごとの終わりの判定基準 | 判定に使う具体（誰に何を聞くか） |
| 90日の工程と各日の出口 | どの業務をパイロットに選ぶか |
| 会議同席時の観察の観点（Dの作り方） | 決裁の詰まりが誰か |
| 業務観察→手順化のフォーマット（Eの作り方） | 業務固有の例外 |
| AIへの読ませ方の型（Hの作り方） | 読ませる中身 |
| 研修カリキュラムと教材 | — |
| 引き渡し手順と更新ルールの雛形 | — |
